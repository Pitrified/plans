# Lab run - 2026-10-10

A capture of a dry run of phases 1, 2, 3 and 5 on a machine that is not g7: a
cloud container (Ubuntu 24.04, 2 cores, 7 GB RAM, root, no systemd, no KVM).
Side-document of phase 1: no status. Nothing here changes g7; it tests the
scripts and the claims in the plans before g7 is touched.

The scripts it produced are in `sandbox-vm/` at the root of this repo.

## What the machine could and could not do

- No `/dev/kvm`: the kernel has KVM built but no device registers. Incus
  refuses to run VMs without it (`Instance type not operational`), and has no
  software-emulation fallback.
- No btrfs or zfs in the kernel, so the pool is `dir`.
- No image servers reachable. The guest was built with `debootstrap` from the
  Ubuntu archive and imported as a local image.
- Outbound traffic is an allowlist: from a guest, "the internet" was the Ubuntu
  archive over HTTP and nothing else.

So the run was split in two:

| Part | Stand-in | What it can prove |
| ---- | -------- | ----------------- |
| Incus: bridge, ACL, profile, volumes, `incus file`, snapshots, the wrapper | an Incus **system container** on the real bridge | everything about Incus except the `--vm` flag |
| The guest: cloud-init, disks, SSH | a real VM under **QEMU software emulation**, its NIC a tap on the same bridge | the cloud-init file as written, on a real kernel with real block devices |

Neighbours the sandbox must not reach were faked with network namespaces: a
"LAN device" at `192.168.50.2`, a "tailnet peer" at `100.64.0.2`, and listeners
on every address of the host.

## Results

### Phase 1 - network

Control first, with no ACL: all six blocked targets were **reachable**. The
stand-ins work, and a bridge with NAT and no rules isolates nothing.

With the ACL from the plan:

```
ok   dns resolves
ok   internet reachable
ok   10.77.0.1:8022 blocked        host, bridge address
FAIL 192.0.2.2:8022 is REACHABLE   host, an address outside the blocked ranges
ok   192.168.50.1:8022 blocked     host, LAN address
ok   192.168.50.2:8000 blocked     LAN device
ok   100.64.0.1:8022 blocked       host, tailnet address
ok   100.64.0.2:8000 blocked       tailnet peer
```

- **The ACL is not enough to keep the sandbox off the host.** It filters by
  destination range, so the host is unreachable only through addresses inside
  those ranges. Any other address the host holds (a public IPv4, in the lab the
  container's own `192.0.2.2`) stays open. Fixed with `host/host_guard.nft`:
  an input-hook rule dropping anything new from the bridge to the host except
  DHCP and DNS. With it, all eight checks pass.
- **Confirmed: a `drop` beats an `allow`**, as the plan assumed. The "drop the
  private ranges, allow the rest" pair works as written.
- **Confirmed: DHCP and DNS survive the drop of `10.0.0.0/8`.** Incus adds its
  own accept rules for ports 53 and 67 ahead of the ACL chain.
- **The ACL covers the whole bridge, not one instance.** Incus renders it as
  `iifname "sbxbr0"` rules, so the QEMU VM's tap, which Incus knows nothing
  about, was filtered the same way. Anything plugged into the bridge is
  internet-only.
- **Inbound is closed too.** The LAN stand-in could not open a connection to
  the sandbox; the host could.
- **The test could pass falsely.** With the instance stopped, every "must be
  blocked" check succeeded, because a failed `incus exec` looks like a failed
  connection. The script now refuses to run if it cannot exec in the guest.

### Phase 2 - guest

In the real VM, with `guest/cloud-init.yaml` unchanged from what g7 will use:

```
vda     6G                root     /
vdb     2G incus_caches   caches   /home/ai/.cache
vdc     2G incus_projects projects /home/ai/projects
```

- User `ai`, passwordless sudo, key login works, password login refused.
- cloud-init finished about 95 seconds after power-on under emulation.
- **`fs_setup` was dropped** for a small script, `sbx-disks.sh`. `fs_setup`
  needs device names, which were the open pitfall in the plan. The script
  matches each disk by its serial and labels it; mounts are by label.
- **First draft of that script was wrong**: it labelled blank disks in the
  order found, so "projects" could land on the caches volume. Noticed while
  setting up the VM with the two disks attached in the opposite order on
  purpose, and rewritten before it ever ran. The version that booted matches
  the serial and guesses nothing; with caches attached first, each label still
  landed on the right disk.
- **Rebuild keeps the volumes.** Root disk deleted and recreated, same two
  volumes attached: the marker files were intact, nothing was reformatted, and
  a file in the home directory was gone, as intended.
- `/dev/kvm` exists in the emulated guest. That says nothing about g7 and was
  not pursued.

### Phase 3 - git flow and credentials

Against the container, through the `sbx` wrapper:

- `sbx in` on a new project, the assistant commits on `main` and on a new
  `feat/x`, `sbx out` shows the commits and fast-forwards. Host working tree
  followed. A branch not checked out on the host is updated without a checkout.
- Uncommitted changes in the sandbox: `sbx in` is refused by git
  (`Working directory has unstaged changes`), and goes through once cleaned.
  An untracked file that the push would overwrite is refused the same way.
- Host and sandbox both commit on one branch: `sbx out` stops with "diverged".
- **`updateInstead` works on a freshly initialised repo**, so the first-time
  flow is `git init -b <branch>` then a plain push. The separate checkout step
  in the plan was not needed.
- The sandbox has no remote, no credential helper, no key of its own, and no
  agent (`Could not open a connection to your authentication agent`).
- Commits come out authored by whatever identity `provision.sh` set.
- Fake `.credentials.json`, `.claude.json` and `sbx.env` were carried out,
  across a rebuild, and back in: mode 600, owned by `ai`, contents identical.
  `incus file push --create-dirs` leaves the parent directories owned by root;
  the wrapper chowns them.

### Phase 5 - rebuild, snapshots, web apps

- `sbx rebuild` end to end in about 75 seconds (container, base provisioning
  only): guard, carry out, snapshot, delete, create, cloud-init, provision,
  carry in, isolation test.
- The guard works: with one unfetched commit in the sandbox the rebuild
  refused and named the project and branch.
- Snapshot keys accepted (`snapshots.schedule`, `snapshots.expiry`). A deleted
  project came back from a snapshot. **Restore needs the instance stopped**:
  `Cannot restore custom volume used by running instances`.
- Web app on `0.0.0.0` in the sandbox: reachable from the host by address. On
  `127.0.0.1`: refused directly, reachable through `ssh -L`. From the tailnet
  stand-in: reachable through a `socat` forwarder on the host's tailnet
  address, unreachable directly.

## Mistakes made on the way, worth not repeating

- A wrong Incus image template (`\n` inside a template string) made the
  container fail in its pre-start hook. Lab image only.
- `incus launch` and `incus exec` can block on an inherited stdin when run from
  a script. Every call in the wrapper passes `</dev/null` where it does not
  need input.
- The debootstrap image had no `lsb-release`, so cloud-init wrote apt sources
  for a release called `UNAVAILABLE`. Lab image only; real Ubuntu images have it.

## Not covered

- An Incus instance created with `--vm`: block volumes attached through a
  profile, the serials Incus gives them, secure boot off, cloud-init delivered
  by Incus to a VM.
- Phase 4 entirely: no GPU, no GRUB, no reboot.
- Nested KVM and the Android emulator.
- btrfs: snapshot cost and scheduled snapshots actually firing.
- `provision.sh` beyond its `base` section.
- Tailscale itself: the stand-in has the address range, not the routing rules
  Tailscale installs.
- Docker on the same host as the bridge.
